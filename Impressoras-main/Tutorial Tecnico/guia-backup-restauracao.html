Backup e restauração do banco no Docker

Um roteiro prático para salvar uma cópia do MariaDB, restaurá-la quando necessário e localizar as credenciais sem colocá-las nos comandos.

Você vai aprender a: confirmar os containers, exportar um arquivo SQL para o Windows, restaurar esse arquivo e validar o serviço depois.

Ambiente deste projeto: Docker Compose · MariaDB 11.4 · PowerShell no Windows

Antes de começar

1

Abra o terminal na pasta do projeto

Execute os comandos na pasta printer-monitor, onde está o docker-compose.yml. A partir da raiz atual do workspace:

Set-Location .\Impressoras-main\printer-monitor
2

Confira se o banco está ativo

docker compose ps

O serviço chama-se db e o container, printer-monitor-db. Para iniciar o banco:

docker compose up -d db
As senhas têm papéis diferentes
  • DB_ROOT_PASSWORD: senha administrativa do MariaDB, usada internamente neste guia.
  • DOCKER_DB_PASSWORD: senha da conta que o aplicativo usa para conectar ao banco.

Os valores configurados ficam em printer-monitor/.env. Não publique nem envie esse arquivo. Os comandos leem a senha de root do container, sem mostrá-la na tela.

1 · Exportar uma cópia

O backup será gravado na Área de Trabalho com data e hora no nome. Primeiro, o MariaDB cria um arquivo temporário no container; depois o Docker copia esse arquivo para o Windows.

Execute bloco por bloco no PowerShell:

docker compose exec -T db sh -c 'mariadb-dump --single-transaction --routines --events --triggers -u root -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE" > /tmp/printer-monitor-backup.sql'

Copie o dump para a Área de Trabalho:

$backupFile = Join-Path $env:USERPROFILE ("Desktop\printer-monitor-" + (Get-Date -Format "yyyyMMdd-HHmmss") + ".sql")
docker cp printer-monitor-db:/tmp/printer-monitor-backup.sql $backupFile

Confirme que o arquivo existe e tem tamanho maior que zero:

Get-Item $backupFile | Select-Object Name, Length, LastWriteTime

Depois de confirmar, remova o temporário dentro do container:

docker compose exec -T db rm -f /tmp/printer-monitor-backup.sql
Resultado esperado

Um arquivo como printer-monitor-20260930-153000.sql na Área de Trabalho. Guarde outra cópia em local protegido. O arquivo contém dados do sistema.

2 · Restaurar uma cópia

Atenção: a restauração substitui tabelas

O dump deste guia contém instruções para recriar as tabelas que estão no backup. Durante a restauração, a aplicação ficará parada e os dados atuais dessas tabelas serão substituídos. Faça outro backup antes se houver qualquer dúvida.

1

Escolha e valide o arquivo

Troque o nome de exemplo pelo arquivo real da sua Área de Trabalho:

$backupFile = Join-Path $env:USERPROFILE 'Desktop\printer-monitor-20260930-153000.sql'
if (-not (Test-Path $backupFile)) { throw "Arquivo de backup nao encontrado: $backupFile" }
2

Pare a aplicação

docker compose stop app

O banco continua ligado; apenas o aplicativo para de gravar enquanto os dados são restaurados.

3

Copie e importe o arquivo

docker cp $backupFile printer-monitor-db:/tmp/printer-monitor-restore.sql
docker compose exec -T db sh -c 'mariadb -u root -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE" < /tmp/printer-monitor-restore.sql'

A senha é lida do container; não a escreva diretamente no comando.

4

Limpe o temporário e retome o app

docker compose exec -T db rm -f /tmp/printer-monitor-restore.sql
docker compose start app

3 · Verificar se voltou

Confira o estado dos serviços:

docker compose ps

Liste as tabelas do banco:

docker compose exec db sh -c 'mariadb -u root -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE" -e "SHOW TABLES;"'

Se o aplicativo não iniciar, consulte as mensagens recentes:

docker compose logs --tail=50 app

Abra também a aplicação no navegador e confira alguns registros conhecidos. O comando de importação terminar não é, por si só, confirmação de que tudo voltou corretamente.

Erros comuns e como agir

“No such file or directory” ao copiar o backup

Confirme o caminho com Get-Item $backupFile. Na restauração, a variável precisa apontar para um arquivo SQL existente no Windows.

“No such container: printer-monitor-db”

Inicie o banco com docker compose up -d db, confira docker compose ps e execute na pasta que contém o Compose.

“Access denied”

Confirme que o banco está ativo. Veja DB_ROOT_PASSWORD no .env; não publique o valor. Alterar o `.env` depois que o volume existe não troca automaticamente a senha gravada no MariaDB.

A importação falha no meio

Mantenha a aplicação parada. Leia a mensagem, confira se o arquivo está completo e preserve o estado atual antes de tentar novamente. Um dump feito por outra ferramenta pode não incluir instruções para recriar as tabelas.

Importante sobre os scripts SQL do projeto

O Compose monta SQLInformation/printer_monitor.sql e alguns scripts de database no diretório de inicialização do MariaDB. Eles rodam quando o volume de dados é criado pela primeira vez. Subir o container novamente ou editar esses scripts não reaplica alterações em um volume existente.

O volume persistente chama-se printer_monitor_db. Não use docker compose down -v como tentativa de restauração: a opção -v apaga o volume e os dados guardados nele.

Checklist rápido

  • Estou na pasta que contém o docker-compose.yml.
  • O container do banco está ativo.
  • O backup existe no Windows e tem tamanho maior que zero.
  • Antes de restaurar, parei o app e preservei o estado atual se necessário.
  • Depois da importação, conferi os serviços, tabelas e dados no sistema.
